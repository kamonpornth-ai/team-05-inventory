# Spec: ฟีเจอร์แจ้งเตือนสต็อกต่ำ และรายงานมูลค่าสต็อก

## 1. เป้าหมาย (Goal)
เพิ่มความสามารถให้ระบบ Inventory ของร้านอุปกรณ์วิศวกรรม สามารถแจ้งเตือนผู้จัดการผ่านทาง Email และ SMS (จำลองผ่าน print) ทันทีเมื่อสินค้าใดมีจำนวนคงเหลือต่ำกว่าเกณฑ์ขั้นต่ำ (Threshold) และสามารถสร้างรายงานสรุปมูลค่าสต็อกสินค้ารวมแยกตามหมวดหมู่ได้อย่างถูกต้อง รวดเร็ว

## 2. User Stories

| รหัส | User Story |
|---|---|
| **US-01** | As a พนักงานคลังสินค้า, I want บันทึกการรับเข้า/จ่ายออกสินค้าพร้อมอัปเดตสต็อกทันที, so that สต็อกในระบบสะท้อนจำนวนจริงตลอดเวลา |
| **US-02** | As a ผู้จัดการ, I want รับการแจ้งเตือนทันทีเมื่อสินค้าใดต่ำกว่า threshold, so that สามารถวางแผนสั่งซื้อสินค้าเพิ่มได้ทันก่อนของหมด |
| **US-03** | As a ผู้จัดการ, I want ดูรายงานมูลค่ารวมของสต็อกสินค้าแยกตามหมวดหมู่, so that นำไปใช้วิเคราะห์และตัดสินใจด้านการเงินและจัดซื้อ |
| **US-04** | As a ผู้จัดการ, I want กำหนดค่าเกณฑ์แจ้งเตือนสต็อกต่ำ (Threshold) รายสินค้าได้, so that เหมาะสมกับอัตราการใช้งานของสินค้าแต่ละชนิด |
| **US-05** | As a ผู้ดูแลระบบ, I want สามารถเปิด/ปิด หรือเพิ่มช่องทางการแจ้งเตือน (Email, SMS) ได้ง่าย, so that รองรับการขยายช่องทางติดต่อในอนาคต |

## 3. Acceptance Criteria (Given-When-Then)

### AC ของ US-01: บันทึกรับ/จ่ายสินค้า
```gherkin
Scenario: รับสินค้าเข้าสต็อก
Given สินค้า "คีมปอกสายไฟ" มีสต็อกเดิม 10 อัน
When พนักงานบันทึกรับเข้า 15 อัน
Then สต็อกคงเหลือใหม่ต้องเป็น 25 อัน
And มีการบันทึกประวัติ Transaction การรับเข้าถูกต้อง

Scenario: จ่ายสินค้าออกจากสต็อกกรณีสินค้ามีเพียงพอ
Given สินค้า "คีมปอกสายไฟ" มีสต็อกเดิม 25 อัน
When พนักงานบันทึกจ่ายออก 5 อัน
Then สต็อกคงเหลือใหม่ต้องเป็น 20 อัน

Scenario: จ่ายสินค้าออกจากสต็อกกรณีสินค้าไม่เพียงพอ
Given สินค้า "คีมปอกสายไฟ" มีสต็อกเดิม 5 อัน
When พนักงานบันทึกจ่ายออก 10 อัน
Then ระบบต้องปฏิเสธการทำรายการและแจ้งเตือน "สินค้าคงเหลือไม่พอ"
And สต็อกคงเหลือต้องเป็น 5 อันเท่าเดิม (ไม่ติดลบ)
```

### AC ของ US-02: แจ้งเตือนเมื่อสต็อกต่ำกว่า Threshold
```gherkin
Scenario: จ่ายสินค้าจนสต็อกต่ำกว่า threshold
Given สินค้า "สายไฟ 2.5 sq.mm" มีสต็อก 20 เมตร และ threshold = 15
When พนักงานบันทึกจ่ายออก 8 เมตร
Then สต็อกคงเหลือเป็น 12 เมตร
And ระบบส่งการแจ้งเตือนถึงผู้จัดการผ่านทาง Email และ SMS ว่าสต็อกต่ำ

Scenario: จ่ายสินค้าโดยสต็อกหลังจ่ายเท่ากับ threshold พอดี (Edge Case)
Given สินค้า "สายไฟ 2.5 sq.mm" มีสต็อก 20 เมตร และ threshold = 15
When พนักงานบันทึกจ่ายออก 5 เมตร
Then สต็อกคงเหลือเป็น 15 เมตร
And ระบบต้องไม่ส่งการแจ้งเตือน (เพราะไม่ต่ำกว่า threshold)

Scenario: จ่ายสินค้าโดยสต็อกยังสูงกว่า threshold
Given สินค้า "สายไฟ 2.5 sq.mm" มีสต็อก 50 เมตร และ threshold = 15
When พนักงานบันทึกจ่ายออก 10 เมตร
Then สต็อกคงเหลือเป็น 40 เมตร
And ระบบต้องไม่ส่งการแจ้งเตือน
```

### AC ของ US-03: รายงานมูลค่าสต็อกแยกตามหมวดหมู่
```gherkin
Scenario: คำนวณรายงานมูลค่าสต็อกสินค้าที่มีข้อมูลหลายหมวดหมู่
Given มีสินค้าในหมวด "Electrical" จำนวน 2 รายการ มูลค่ารวม 5,000 บาท
And มีสินค้าในหมวด "Hand Tools" จำนวน 3 รายการ มูลค่ารวม 3,500 บาท
When ผู้จัดการสั่งพิมพ์รายงานมูลค่าสต็อก
Then ระบบต้องแสดงมูลค่ารวมแยกตามแต่ละหมวดหมู่ถูกต้อง (Electrical = 5,000, Hand Tools = 3,500)
And แสดงมูลค่ารวมของทั้งระบบถูกต้องเป็น 8,500 บาท

Scenario: รายงานมูลค่าสต็อกกรณีระบบยังไม่มีสินค้า
Given ระบบยังไม่มีรายการสินค้าในสต็อก
When ผู้จัดการสั่งพิมพ์รายงานมูลค่าสต็อก
Then ระบบต้องแสดงข้อความ "ไม่มีสินค้าในระบบ" และแสดงยอดรวมเป็น 0.00 บาท โดยไม่เกิด error
```

## 4. In Scope / Out of Scope

* **In Scope:**
  - จัดการข้อมูล Product, Category, Stock Transaction ในหน่วยความจำ (In-Memory)
  - ฟังก์ชันรับเข้า (Receive), จ่ายออก (Issue), และตรวจสต็อก
  - ระบบแจ้งเตือนหลายช่องทาง (Email, SMS) โดยจำลองด้วย `print` ตามรูปแบบที่กำหนด
  - ระบบคำนวณและสร้างรายงานสรุปมูลค่าสต็อกแยกตามหมวดหมู่
* **Out of Scope:**
  - การเชื่อมต่อ SMTP เซิร์ฟเวอร์จริง หรือ SMS Gateway ผู้ให้บริการภายนอก
  - ระบบ Login / Authentication และสิทธิ์ผู้ใช้งาน (Role-based access)
  - ฐานข้อมูลภายนอก (SQL/NoSQL)

## 5. Functional Requirements (FR)

| รหัส | ความต้องการเชิงหน้าที่ | เชื่อมโยง Story |
|---|---|---|
| **FR-01** | ระบบต้องอัปเดตยอดสต็อกทันทีเมื่อมีการทำรายการรับเข้า/จ่ายออก | US-01 |
| **FR-02** | ระบบต้องตรวจสอบจำนวนคงเหลือก่อนจ่ายออก และปฏิเสธทันทีหากไม่พอ | US-01 |
| **FR-03** | ระบบต้องตรวจสอบเงื่อนไขสต็อกต่ำ (`quantity < threshold`) และแจ้งเตือนอัตโนมัติ | US-02 |
| **FR-04** | ระบบต้องรองรับการกระจายข้อความแจ้งเตือนไปยังหลายช่องทาง (Email, SMS) | US-02, US-05 |
| **FR-05** | ระบบต้องสามารถคำนวณผลรวมมูลค่าสต็อก (`quantity * unit_price`) แยกตามหมวดหมู่และยอดรวมทั้งสิ้น | US-03 |

## 6. Non-Functional Requirements (NFR)

| รหัส | มิติ (Quality Attribute) | ความต้องการเชิงคุณภาพ (วัดผลได้) |
|---|---|---|
| **NFR-01** | **Performance** | ประมวลผลและแสดงรายงานมูลค่าสต็อกสำหรับสินค้า 1,000 รายการ ได้เสร็จสิ้นภายใน 1 วินาที |
| **NFR-02** | **Maintainability (Extensibility)** | สามารถเพิ่มช่องทางแจ้งเตือนใหม่ (เช่น Line Notify, Slack) ได้โดยไม่ต้องแก้ไขโค้ด Business Logic เดิม |
| **NFR-03** | **Reliability & Robustness** | ป้องกันข้อมูลติดลบ (No Negative Stock) และรองรับกรณีค้นหาไม่พบโดยไม่ทำให้ระบบ Crash |

## 7. Design Notes & Architectural Guidelines
1. **Separation of Concerns:** แยกส่วนการคำนวณสต็อก (Business Logic) ออกจากกลไกการส่งแจ้งเตือน (Notification I/O) อย่างเด็ดขาด
2. **Design Patterns:**
   - **Observer Pattern:** ใช้ในการเชื่อมต่อระบบแจ้งเตือนเข้ากับ Inventory Service เพื่อให้รองรับ Notification Observers หลากหลายช่องทาง
   - **Factory Pattern:** ใช้สำหรับสร้าง Instance ของ Notifier ตามประเภทที่ระบุ
